# Testing

Guided restore must verify the selected full snapshot, preview without changing the
target, retain the entire current vault and restore the exact older tree. Cover upgrade
receipts, listing/filtering/incomplete backups, corrupted entries, hidden and
binary files, BOM/CRLF notes, empty folders, runtime links and file/directory changes.
Test missing/damaged target settings, a missing vault, no-op restores and undo via
the pre-restore backup. Inject copy, receipt and rename failures, including an
interruption immediately after each move and concurrent edits at the target. Keep
current edits and report manual recovery instead of overwriting them. Test direct
`--restore` before Session loading, menu 13 exiting after an old snapshot, cancellation
and invalid arguments. Run packaged CLI acceptance against real old archives and
receipts generated by the previous upgrade engine. Use disposable local vaults only.

Guided upgrades use a temporary copy and a complete external backup. Exercise the
real migrate/update/configure engines with legacy layout, missing old fieldbook.json,
custom notes/settings/README, binaries, hidden files, empty folders and runtime
symlinks. Assert preview/cancel leaves the target unchanged, and verify every backup
entry before application. Test keep-settings, work manager and combined/custom
setups, CLI bootstrap and main-menu reload. Inject backup/copy corruption, stale
target/stage snapshots, partial apply failure and concurrent edits during rollback.
Restore only files still matching the upgrader's writes; keep a complete backup and
report conflicts. Refuse overlapping destinations, bad release hashes and downgrades.
Future releases need real archived-vault upgrade acceptance in addition to fixtures.
Use every starter profile as the **release source**, both extracted and zipped,
as well as testing it as a target. Disabled commands must be recovered only from
catalogued, manifest-verified canonical copies. Check rendered/customized source
dashboards, absent or corrupt/linked recovery copies, forged activation hashes,
unverified catalogs and ordinary missing kit files. Source notes/settings must not
enter the canonical input, sources must remain unchanged, and target integrations
must remain off. Exercise the manual updater as well as the guided CLI.

Audit sequential upgrades, not only one old-to-new jump. A pristine modern vault
must not rewrite historical TaskNotes paths. A genuine legacy migration must update
pristine rules/templates instead of misclassifying its own edits as customizations;
real custom content must remain. Never rewrite .fieldbook recovery/proof/backup
files. Refresh general merge candidates only when the prior manifest proves them;
edited candidates still block. Cover missing PyYAML before staging, the exact old
unused Jira placeholder and single-account identity migration, explicit preserved
removals and TaskNotes custom-default warnings. Test all enabled work connections
without network calls, switch combined setups to manager, rerun unchanged, and
restore/undo each archived upgrade.

Credential guides in `tools/integration-guides.json` must cover every registered
provider and every supported variant. Run the real menu with fake input/output and
a recording browser opener. Cover Enter/back/cancel, only explicitly selected
official links, malformed catalogs/unsafe URLs, browser failure and accidental
secret input without echoing it. Assert unchanged vault snapshots and no calls to
password, credential, OAuth or connection-test dependencies. Exercise main-menu 11,
guided-menu 9 and `--credential-guide [provider]`. Instruction completion must stay
separate from verified credential/read status. Review official source links when
updating the catalog; mock tests do not validate a provider's live portal UI.

The guided integration checklist must remain usable with no accounts or credentials.
Exercise every registered provider through requirements, explicit read tests and
failure/incomplete states. Pending edits must block remote actions; Canvas must
retain its school activation gate. Test the direct CLI entry points and Outlook
local-only guidance. For both calendar providers, run the real OAuth, calendar
read and Series-binding engines through the menu using fake HTTP/browser/OS stores.
Keep tokens out of menu output and vault backups. An unconfigured starter connection
must not block selecting a separate configured account. These are offline fixtures,
not live sign-in evidence. Future adapters follow `tools/ADDING-INTEGRATIONS.md`.

Python 3.10+ is the maintained user scripting runtime; PowerShell is not required.
AI assistant runs its JavaScript tool wrappers and plugins itself. Node.js 22+ is only
needed for JavaScript tests or the optional standalone tracker CLI.
Install fieldbook_core/requirements.txt in a Python venv and standalone JavaScript dependencies with `npm install --ignore-scripts --no-save` run from the `fieldbook_core` folder.

```text
python -B -m unittest discover -s tests -p '*_test.py'
python tools/manage-vault.py health
node --test tests/*.test.mjs
python tools/make-manifest.py .
node tools/validate.mjs .
```

Use the venv Python in these commands. Tests use temporary fixtures and mocked HTTP,
Git execution or plugin downloads. No live tracker requests, commits or accounts.
The regex test deliberately exercises a pathological expression. New-file creation
uses hard links; test the actual local/sync filesystem before relying on it.

Release validation covers JSON, Bases YAML, JavaScript syntax, skill metadata,
embedded view references and manifest hashes. Deployment is from verified clean
release files and pristine settings seeds, never from a user's Inbox/credentials.
The Python maintenance tests cover setup, migration preview/collisions/links,
updater preservation, hash checks, backfill, pending manual conversions, legacy
script retirement, archive traversal, capture and health-check failures.

Manual acceptance: open a disposable starter in Obsidian, accept trust deliberately,
check the plugins/views, create/schedule/block/complete a task, verify root Tasks/Views,
and try a template with punctuation/existing names. Insert into an existing named
note in Editing view; verify saved properties and complete body headings. Also run
Templater: Create new note from template from Reading view and verify any title
prompt, destination and full body. Do not count frontmatter-only output as success. In AI assistant check commands,
skills and custom tools, prompt-free reads/searches, write approval/denial and hash
conflicts, plus native shell/file/web denial. Check /help only describes its target,
and optional accomplishment/link suggestions wait for acceptance. Test /list and
/item without duplicating task state. Tk capture UI is optional and needs a Python
build with tkinter. Repeat UI and filesystem checks on each supported platform.

For authorized live trackers verify linked/mine scope, pagination, mappings, one
reviewed local edit and repeated-sync idempotence. Trackers stay read only. Fixtures
do not certify live authentication, rendering, host permission UI or model judgments.

## Four-provider checks

New fixture coverage exercises GitHub issue identity/PR exclusion/paging/closure
reasons, Azure query/batch/date fields, allowed read routes, and failures without
partial success. Service tests exercise every provider in core/personal/school/work
setups and derive self/report scopes from person records without manager links.
Missing/duplicate identities and config conflicts fail before remote requests.
Python tests verify relationship queries, readable but protected provider configs,
feature switching and preservation of existing connections during upgrades.

For optional live acceptance: configure a disposable vault with your read-only
token, use one known linked issue/work item, compare its ID/state/assignees with
the website, then try mine and team with the reviewed person roster. Approve one
local change, repeat the sync, and confirm no duplicate note/log. Live Azure/PAT
and GitHub token permissions cannot be proven by offline fixtures.

## Person templates

Check the real Person template through automatic stub creation, not just a fixture
copy: stubs must not acquire report relationships from work/manager settings.
Create one note from each shipped profile; person matching and self/report scopes
must depend on tags/relationships, not filenames or template choice. Upgrade tests
verify that old unmodified Work person is retired, customized templates and person
notes survive, preview writes nothing and a repeated update is idempotent.
For a manual check, insert each template into a new People/ note and check its
embedded tasks/meetings/reviews. No live UI pass is claimed by these tests.

## Neutral defaults

Automated tests render all 22 shipped templates with a small Templater fixture,
parse their YAML, and exercise real prompt sanitization, cancellation and filename
collisions. They write/query/link shared template records through the notebook
Python tools in core, personal, work, school and combined contexts. They also
check that unfiltered inventory/overview includes blank/missing and disabled areas,
and that a requested local edit preserves legacy specialized fields and history.
A fixture render does not certify Obsidian UI rendering or an AI's interpretation.

Use these prompts for model acceptance in a disposable vault; inspect the draft
before approving a write. These are scenarios, not claims of completed live tests.

| Context / prompt | Expected behavior |

| Core: /study practice guitar using these notes | Ordinary study tasks; no school setup, syllabus, exam or course requirement |
| Personal: /item borrowed drill from Sam | Neutral Item, supplied loan/owner context; no assumed purchase, ownership or warranty |

## Dashboards and views

The Python view suite parses the actual shipped Base expressions and evaluates
filters over dated/link-aware note fixtures. Its small strict interpreter covers
the documented syntax used here, including global + view AND semantics, missing
properties, links, list filters and date arithmetic. Unsupported syntax fails the
test. This is a fixture model, not Obsidian's native Bases engine or a rendering test.

Checks include all areas and blank/missing area, template/example exclusions,
one-off deadline/completion boundaries, dropped/future/recurring records, optional
course/manager/review embeds, explicit self/report identity, wrong-kind assignees,
exact one-level project links, Jira opt-out/project context, neutral Items/Lists,
open research ideas, closed opportunities and standalone meeting views.

Manual acceptance: use a disposable combined vault with one task per area plus an
unset-area task, a report/peer/classmate, and an optional course. Open Dashboard and
each area page; confirm correct rows and readable columns. Open every Base's first
view, then optional tabs. Check blank-area groups, a self note's task embeds, a
project with a path-qualified/aliased child link, and the manager report-task view.
Edit a linked person's relationship/status and reopen the Base to refresh it.
Complete a recurring instance in TaskNotes and confirm it is not a one-off completion
row. Open a saved review only via an explicit review tab/page. No setup choice should
rewrite notes or hide saved records from the shared inventory.

- `python tools/configure.py --check` must not write or touch credentials/network.

## Read-only connection diagnostics

Use mocked transports and credential readers for automated diagnostic coverage;
never use a real key or require a network account in the regression suite. Cover
Jira Cloud/Data Center, Agility, GitHub, Azure, Canvas, Google and Microsoft separately:

- `--check` remains offline and never retrieves a secret. `--test` reads saved
  settings only; tests do not change feature flags, even for disabled integrations.
- `--test all` skips empty instances and untouched starter URLs. An explicit
  unconfigured provider/unknown instance must not report success. `--instance`
  requires a named provider, and `--check` cannot be combined with `--test`.
- Successful URL/authentication stages cannot substitute for the selected scope
  read. Missing scope stays unverified. Include an authenticated empty query and
  inaccessible/missing repository, project, filter and Canvas course cases.
- Check exit codes: 0 for required checks passed, 1 for failure, 2 for incomplete
  or all-skipped results. Optional unknown identity can coexist with a verified
  protected read; missing required scope cannot. A passed configured provider with
  other unconfigured providers skipped may still exit 0.
- Exercise 401, 403, 404, rate limits, redirects, TLS/network failures, timeouts,
  unexpected HTML and malformed/oversized JSON. Messages must be sanitized;
  synthetic secrets, Authorization headers and raw response bodies never appear.
- Environment and OS-store credentials follow their saved mode; a missing/locked
  OS store does not fall back to an environment token. Changed connection binding
  must not reuse an old stored key. Only allowed read routes are called, including
  the documented Agility query/Azure WIQL read POSTs; never probe a write endpoint.
- Interactive tests use saved configuration and reject unsaved edits. The
  after-Save test defaults to No. Capture before/after vault bytes to prove a test
  does not write settings, notes, backups or downloaded content.

Optional authorized live acceptance: run
`python tools/configure.py --test <provider> --instance <id>` against one narrow saved connection. Check every reported stage,
then read one known item through the normal workflow. Record provider/instance and
sanitized outcomes only. A green read check proves the reported operation worked;
it cannot prove that a token is read-only, that every record is accessible, or that
all other provider endpoints work. Inspect token permissions in the provider's UI.
Do not perform a remote write as an authorization test.

Calendar diagnostics can refresh an existing approved OAuth grant in the OS keyring;
they must not launch interactive sign-in, save token files, enable a feature or write
the vault. Keep this credential refresh separate from the no-vault-writes assertion.

## Guided project selection

Run `python -B tests/integration_projects_test.py` for the saved-connection picker
fixtures. Cover each provider's real helper with a fake transport and no live key:
Jira Cloud/Data Center projects, Agility Scope query, GitHub repositories with Issues
enabled, Azure projects, and Canvas active courses. Assert fixed read routes,
validated IDs, correct settings patches, preserved API context paths, one request,
50-choice bound, first-page and continuation notices, sanitized labels/errors,
and no config, credential, feature or note writes. Redirects and pagination links
must never be followed. An unavailable list must leave manual entry possible.

Wizard scenarios should add a connection, Save, use numbered provider/instance/scope
choices, review the patch, Save again, optionally test, then Exit. Check that Save
returns to the menu and Exit discards only later staged edits. Test add/replace for
GitHub/Canvas, replacement warnings for Jira/Agility, the 10-course limit, cancel,
stale saved configuration, and pending edits/credential updates blocking discovery.
Successful listing is not evidence of issue/assignment access.

Every new direct provider must join this central configuration CLI: connection and
scope fields, safe credential references, feature activation rules, preview/Save,
read-only diagnostics, documentation and fixture tests. Add bounded scope discovery
where the provider offers a suitable read API; otherwise explain manual entry.
Do not require users to hand-edit JSON for normal setup or add a write probe to test
permissions. Provider UI coverage must exercise the actual helpers with mocked HTTP,
not only substitute a stub that returns the expected menu choices.

Record-specific binding checks must use actual Project/Course fixtures. Menu 8
should select one local record, saved provider/instance, and discovered or manual
scope; preview/apply updates only its allowed metadata with a backup. Preserve the
body, other provider bindings, unrelated records and instance defaults. Cover
cancel/no-op, concurrent edits, path traversal/linked files, malformed metadata and
unsafe instance/course rebinds. Two Canvas instances with course ID `123` must
remain distinct and use their own credentials.

Tracker service tests cover `projectScope` for mine/team/all with all four
providers: the remote request uses the bound scope, credentials resolve the original
saved instance, configuration bytes remain unchanged, and unsafe IDs, linked mode
or a simultaneous query fail before any credential/network access. Audit skills
for missing-binding fallback, multiple provider ambiguity, explicit Project-linked
ticket IDs, and Course calls grouped by instance. Run skill-creator's quick validator
after changing the instructions; that check does not establish live model behavior.

## Live calendar and OAuth fixture checks

Exercise Google and Microsoft with mocked token endpoints, read APIs and OS stores;
do not use real sign-in credentials in automated tests. Calendar reads must stay on
their fixed HTTPS provider routes and must never follow join URLs, attachments or
arbitrary pagination links. Cover feature gates, inclusive UTC windows and local
date interpretation, all-day events, moved/cancelled occurrences, case-sensitive
IDs, duplicate occurrences, empty/short pages with continuation, limits and unknown
attendee totals. Description/body previews must disclose incompleteness.

Menu 8 Series links preserve the account/calendar/series identity and standing
agenda; no occurrence Meetings are created. Repeated selected-occurrence capture
must use its original occurrence identity, not a changed start or title. A different
account or calendar is not merged automatically, nor is an ICS UID assumed to have
the same recurrence meaning as a provider's UID.

Menu 9 requires an explicit saved OAuth/keyring connection and `signin`. Test
Google state/PKCE and loopback callback validation, Microsoft device-code expiry,
pending/slow-down/denied responses, token scope checks, refresh rotation, changed
client/tenant binding, and revoked/missing/locked credentials. Tokens and client
secrets must never reach configuration, notes, logs, error bodies or AI results.
Local source/config snapshots should remain unchanged after sign-in and reads;
only the approved OS credential bundle can change. Reject interactive authorization
from the AI read tool. Live account/admin-consent acceptance remains a separate
human test, not a result inferred from these fixtures.

Run the native packaged acceptance script as well as unit tests; use disposable
vaults and mocked providers. A prepared CI job is not evidence it was executed.
